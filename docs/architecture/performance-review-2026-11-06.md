# 性能 review 与本轮优化（2026-11-06）

本轮基于当前工作区检查了路由、GeoIP、DNS/Fake-IP、连接池与转发、策略组、流量统计、桌面列表/持久化/切换节点及 CLI 回归入口。保留工作区原有未提交修改；本轮生产改动仅涉及 `router/geoip.rs` 与 `router/engine.rs`。这是源码审查与局部 CPU 基准，不是所有协议、设备和公网链路的完整性能审计。

## 已落实

### GeoIP 查询索引

此前 `build()` 只按前缀长度排序，每次查询仍线性扫描全部网段。当前内置数据库共 8,515 条记录，DNS 国内地址分类和路由 GeoIP 匹配都会使用它。

现在按前缀长度分组，各组按归一化网络地址排序并二分查找；仅为实际存在的前缀保存索引范围和掩码，不复制国家字符串、不建立逐地址树节点。查询期间不分配内存。复杂度由 O(N) 降为 O(各前缀组的 log N 之和)。

保留最长前缀优先、重复网段先配置者优先、IPv4/IPv6 分离，以及未 build 或 build 后继续添加时的原有顺序扫描语义。补充拒绝越界前缀，避免非法 IPv4 /33、IPv6 /129 被当作有效主机规则。build 可重复执行。

### 路由缓存键

此前每次查询都创建小写主机字符串，再拼接端口；有客户端/TUN 上下文时还要将多个 IP 以 Debug 格式拼成另一字符串。缓存命中同样承担这些成本。

现在使用结构化键，主机名仍做小写归一化，端口、来源 IP、TUN 目标 IP 与国内地址标志直接存储和哈希。省去中间字符串及地址格式化；保持 4096 条 LRU、命中提升顺序、设备/端口隔离，以及域名解析结果不写入无 TTL 路由缓存的原有语义。未宣称整体缓存内存减少：结构化键本体更大，实际内存取决于地址和主机长度。

## 可复现的局部基准

`tools/benchmark-geoip.rs` 是无外部依赖的 Rust 基准，文件顶部提供编译命令。用相同 harness、相同 `rustc -O` 分别编译本轮修改前后的 `geoip.rs`，交替运行 5 轮；每轮预热后查询 200,000 次，IP 预先解析，以 black_box 避免优化掉查询。每个版本的命中数一致。

| 数据及样本 | 修改前中位数 | 修改后中位数 | 比率 |
| --- | ---: | ---: | ---: |
| 8,515 条实际内置网段，8 个 IPv4/IPv6 国内、国外、私网地址 | 4,259.8 ns/次 | 117.8 ns/次 | 约 36.2× |
| 8,192 条合成 /24，1,024 个地址，命中/未命中各半 | 5,353.8 ns/次 | 23.1 ns/次 | 约 231.8× |

合成数据仅有一个前缀长度，对索引特别有利，不能代表日常工作负载；实际内置样本也是固定的小集合。本机结果不能直接推断 ARM 路由器的收益，更不能换算为网页首字节或下载吞吐的同比提升。原始记录和修改前源码保存在 `.local/performance-review-20261106/`。

另做缓存键构建与哈希的隔离微基准：直接抽取修改前后对应源码，使用等价线程局部上下文、DefaultHasher、固定主机名、black_box，每轮 500,000 次、交替运行 5 轮。中位数：无上下文 96.4 → 34.1 ns；IPv4 TUN 349.4 → 41.8 ns；IPv6 TUN 342.5 → 48.3 ns。它不包含 LRU 锁、缓存查找或规则执行，不是完整路由性能。临时 harness 和输出在同一记录目录的 `key-*.rs`、`key-benchmark.log`。

## 审查中保留的现有优化

- 连接池已有预连接和全局预算；TUN 已有批量写入、共享 payload 和背压预算。本轮没有凭猜测增大缓冲或连接数。
- DNS 已有缓存和相同在途查询合并。未更改 TTL、DNS 出口隔离或查询优先级。
- 节点列表已有搜索元数据缓存；桌面持久化已有单写入线程和合并队列。
- 发布参数保持不变。本轮没有将减小二进制体积等同于运行提速。

## 后续优先项（本轮未修改）

1. **桌面 TUN 切换节点的界面阻塞。** `AppState::apply_outbound_hot_swap` 在界面调用路径中同步执行 `resolve_to_ips`，且按策略组逐成员解析，重复成员会重复解析。慢系统 DNS 或较大策略组可能延长卡顿。应把“去重、解析、更新绕行路由”移到后台，再通过代际检查发布对应的出站；不能简单先发布再异步补路由，否则可能让节点连接进入 TUN 回环。需要快速连续切换、解析失败和旧连接保留的专项验证。
2. **Fake-IP 持久化占用 DNS 工作线程。** 新映射触发 `maybe_persist` 时，在同步锁下完成快照、格式化和文件提交。虽有 10 秒节流，慢 flash 仍可能拉长某次 DNS 响应，并让其他待持久化请求等锁。建议单写入者合并快照、后台写入并保留退出 flush；要同时覆盖异常退出、并发保存与地址稳定性，不能仅把写入任务随意 detach。
3. **端到端测量。** 本轮尚未采集新连接首字节、预连接命中率、CPU/GiB 或路由器长时间负载。后续应对新旧版本交替采样，区分冷连接、预热连接、持续传输、并发和公网波动。
