# TUN 开销复查与优化（2026-11-04）

结论：仍有可避免的损耗。本轮定位并修复了客户端 MSS 未被用于发送分段的问题，同时减少逐包分配、读取碎片和 ACK 队列扫描。候选随后经用户授权安装到路由器，人工停止后又按用户后续指示恢复运行。尚不能宣称已测得设备上的提速比例，部署状态见末节。

## TUN 多出的工作

| 路径 | 本地接入到出站之间的工作 |
| --- | --- |
| SOCKS TCP | 内核 TCP → SOCKS 解析 → 字节流中继 → Vision/其他出站 |
| TUN TCP | 内核路由 → TUN 包读取 → IP/TCP 解析、队列与用户态 TCP → 字节流中继 → Vision/其他出站 |

应分别测量逐包 CPU、分配、读写调度、窗口/重传与首连策略。即使出口节点相同，TUN 的目的 IP、fake-IP/SNI 恢复及设备规则也可能改变 DNS 与路由过程。检查某个下载耗时前，必须先确认目的地址、出站和规则相同。

Linux TUN 本身以用户态读写 IP 包提供接口，因此用户态收发及必要的包处理不会因调大缓冲自动消失。参考 [Linux TUN/TAP 文档](https://docs.kernel.org/networking/tuntap.html)。

## P1：未遵守客户端声明的 MSS

原实现读取 SYN 的窗口缩放选项，但没有读取 MSS；新数据仅按本地 TUN MTU 和窗口分段。即使客户端 MSS 为 900，MTU 1500 的 IPv4 路径仍接受并发送 1460 字节。这可能使小 MTU/VPN/Wi-Fi 路径丢弃超出接收上限的段，但没有现场报文证明此前路由器的具体速度问题由它引起。

修复：

- 连接建立时读取客户端 SYN MSS；发送、重传和窗口探测共同经过分段限制。
- 缺少 MSS 时，IPv4 使用 536，IPv6 使用 1220；正常提供 MSS 的现代客户端不使用这些缺省值。
- TCP 选项占用有效载荷空间，同时保留本地 MTU、窗口、本流和全局预算约束。
- 零值作为无效选项忽略；重复有效选项取较小值。后续非 SYN 报文不能改变已确定的接收上限。

缺省值及有效发送 MSS 的要求见 [RFC 9293 §3.7.1](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.7.1)。

新增内存报文测试在修复前 3 项失败，分别复现小 MSS 被忽略、缺省值错误及重复选项未受限。修复后的用例覆盖 IPv4/IPv6、小 MSS、MTU 上限、重传、默认值、重复/零值选项、后续报文携带 MSS、完整分段数据及 ACK 后预算释放。

## P2：不必要的分配与调度

### 包序列化

原来每个发往 TUN 的包都会创建新的 `Vec` 并在写头和追加载荷时增长，启用 PI 时还拼接并前插头部。现在设备任务拥有可复用写缓冲，预留长度后写入头部与载荷；PI 直接先写入缓冲。IPv4/IPv6 和 TCP/UDP 的报文字节一致性与反复复用测试通过。

这减少序列化分配，尚未消除载荷复制、校验和计算或每包设备写入。

### 接收与部分读取

有序接收的首块载荷直接移交给读取队列，避免再次复制。部分读取使用当前位置，不再为每次短读重新分配剩余尾部；整块读完立即释放。

cursor 最多保留一块由当前提取器产生的 8 KiB 数据。因此相对逐次收缩尾部，慢读流可能短暂保留已消费前缀的容量；这是一项有界的 CPU/内存取舍，不能把它宣称为严格降低所有场景 RSS。

读取会合并已经就绪的队列块，最多处理 32 块，不等待更多数据。批量归还字节与块信用，保留 EOF、RST、超时及零窗口恢复行为。可减少 relay 和后续 TLS/Vision 的小块读写次数，实际收益取决于队列是否已有多块数据。

## P2：ACK 处理全队列扫描

原实现每个累计 ACK 会定位所在分段、扫描保留队列，并在清理前后重新求和。现在只处理被确认的前缀，部分确认只裁切首个剩余分段，待确认字节数复用已有的预算计数。

序号回绕、无效/重复 ACK、部分确认、重传计时和预算释放均有回归。新增差分测试逐步比较剩余数据与完整原始字节流，未跳过 ACK 范围校验。

同一 macOS 构建主机的 release 孤立微基准，32,768 次累计 ACK、每轮 256 个在途分段：原版约 **10.61 ms**，优化版约 **1.60 ms**。连接和载荷初始化不计入这一阶段；两边 Tokio、etherparse、ahash 与 ipstack 使用的 rand 版本一致。它只能证明 ACK 队列处理成本下降，不能换算为路由器整机 CPU 或实际下载加速倍数。

## 暂不直接调整的部分

- **MTU、MSS 广告、窗口缩放、RTO**：保留已验证策略。本轮修复对端 MSS 接收处理，不扩大网络 MTU，也不缩短重传定时掩盖丢包。
- **重传数据所有权**：发送队列与重传队列仍存在独立载荷存储。共享载荷可继续研究，但必须同时验证部分 ACK 的内存释放、预算以及引用生命周期。
- **设备批量 I/O / 多队列**：需要保持包边界、流内顺序和控制流量优先级。不能把多个完整 IP 包直接拼成一次普通 TUN 写入。
- **GSO/GRO**：当前解析器按单个、MTU 范围的普通 IP 包工作；开关卸载前需要实现并验证相应元数据、校验和与分段行为。参考 [Linux segmentation offloads](https://docs.kernel.org/networking/segmentation-offloads.html)。
- **Linux 专用透明 socket 入站**：可作为后续架构对照，评估减少用户态 TCP 工作的空间；需另外核对 Merlin 内核、UDP、源地址策略及恢复流程。

## 测量纠偏

此次路由器只读 `trace_route` 对测试域名及实际 IPv4 的保存规则解释均返回 `direct`。因此先前 gstatic HTTPS 的数字不能当作 Vision 代理链路的 TUN 对照。该接口解释保存配置，不能代替逐连接抓包，也没有据此回推所有历史测试的实际路径。

下一步端到端实验应固定同一目标地址、同一出站与数据大小，再对照 LAN 显式代理和透明路径的延迟、吞吐、CPU/GiB、重传及 RSS；此次没有通过切换在线配置构造对照。
