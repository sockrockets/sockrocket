## 现场与测试边界

在 RT-AX86U Pro 的 0.0.18 本地优化构建上排查。起点二进制 SHA256 为 `bf008b59cf5dfb2f22382894ec9e2e778059cf7782d9c316f9bb490a01368a69`，包含前轮 GeoIP、路由缓存、Fake-IP 后台保存和 DNS 池等待修复。配置及节点凭据没有导出到报告。

最初部署后的 18 次访问中，14 次成功：SOCKS gstatic 两次快速 TLS 失败、TUN Google 两次失败。四路同时下载 1 MiB 全部返回 200 且字节数完整。后续 SOCKS 短请求 8/8 成功，不能据此认为间歇故障已消失。

日志显示 UTC 12:52:00 健康检查超时，12:52:20 自动切换节点，12:52:22 重载配置。配置差异只有 `active_node`。因此，部署完成时配置相同，但不能声称整个后测期间节点不变。将原节点和当前节点配置用于两个临时、仅回环监听的独立进程，分别补测 8 次均成功；没有修改主服务节点。

## DNS 与测试路径

路由器 `/etc/resolv.conf` 指向上级路由器 `192.168.1.1`，而不是 LAN 的本地 DNS。上级 DNS 给 `www.google.com` 返回 `31.13.92.37`；通过代理访问 Google DoH 时返回 `142.251.*.119` 的地址集合。本地 DNS 和电脑向路由器查询均返回 `198.18.0.11`，gstatic 返回 `198.18.0.13`。

第二组 SOCKS gstatic 快速失败仍然复现，因此 DNS 差异只能解释一部分现象。两组配置哈希均稳定。第二组数据尚未完整统计时的口头“全部成功”已更正。

## VLESS 预连接假设与已撤回实验

主节点使用普通 VLESS（`flow: null`）。原池在请求到来前完成传输层连接，最多保留 30 秒，取用时做一次非阻塞读检查。VLESS 的认证和目的地址头尚未发送，服务端可能仍在等待认证数据；传输层建连完成不代表代理协议已就绪。

[Xray VLESS 入站源码](https://github.com/XTLS/Xray-core/blob/main/proxy/vless/inbound/inbound.go)在读取协议请求前设置握手截止时间。[官方策略文档](https://xtls.github.io/en/config/policy.html)说明握手超时会中断连接，当前文档默认值为 60 秒；本次没有读取实际节点服务端配置，不能推断它采用该默认值或某个固定的短超时。

用相同已部署源码编译独立测试进程，固定同一节点，同时提供预连接与即时建连两个回环 SOCKS 端口，交替顺序，取用预连接时额外记录年龄和存活检查结果。10 对请求中：

- 预连接：8/10 成功，两次快速 TLS 失败，分别约 0.314s、0.277s。对应池连接闲置约 3.658s、3.729s，检查均返回 `ready=true`。
- 即时建连：9/10 成功，没有快速 TLS 失败；一次触发相同的 5s 连接/TLS 阶段超时。
- 两类连接仍经过同一网络和服务端，缺少服务端日志，不能将所有超时断言为预连接过期。实验支持移除“取出后即失效”的风险路径，不证明整条公网链路无其他故障。

实验方案将普通 VLESS 与 Vision 的外层连接改为按请求建立：拿到目标后立即发送 VLESS 请求头。XHTTP 工厂内部的传输复用保留，其他协议的连接池不改。没有重放用户数据、跳过证书校验或放宽 TLS 校验。正常成功请求可能增加一段建连耗时；原意是消除快速失败及其后续重试，但后续实机结果否定了直接采用该方案的决定。

新增回归测试验证空闲 outbound 不会提前连上等待认证的服务端，实际请求到来后立即发送正确的目标头并读取响应。该测试在修复前失败。另强化 Vision 测试，覆盖正常构造时也不预连接。

原始日志、对照程序和隔离源码位于 `.local/tls-investigation-20261106/`。诊断程序源码与上线候选源码分开，池年龄日志不会编入上线候选。

## 实机失败与回滚（最终结果）

候选启动检查通过，但随后电脑侧真实访问 **TUN 0/10、SOCKS 0/10**，其中 17 次 TLS 错误、3 次超时。健康检查在 UTC 13:30、13:31 反复切换节点。路由器侧新一轮诊断还在本地 DNS 查询阶段就返回错误，未产生有效请求对照表，不能将其计为通过。用户同时反馈电脑无法正常访问并开启本地代理。

立即停止性能实验，使用已校验备份回滚主程序和 API，未修改用户电脑代理设置。运行中主进程 PID 9329、API PID 9177 均验证回到 `bf008b59cf5dfb2f22382894ec9e2e778059cf7782d9c316f9bb490a01368a69`。DNS 53/5300、防火墙、启动脚本校验通过。回滚后 SOCKS gstatic 返回 204（1.774s）、路由器 Fake-IP TUN Google 返回 204（3.227s）、电脑明确绑定 LAN 接口并绕过本地代理访问路由器 Fake-IP Google 返回 204（2.880s）。这些是恢复检查，不代表所有网站均已验证。

工作区 VLESS 改动已反向应用补丁并与改动前副本逐字节核对，保留原先未提交修改。实验补丁、候选、失败日志和回滚清单保留在本地排查目录；路由器上的实验候选和临时对照可执行文件已删除，旧版备份保留。前轮 Fake-IP/DNS/GeoIP 优化仍在运行。

结论：单独、低流量的预连接对照不足以代表实际 LAN 负载。取消预连接没有通过真实环境验收，不能称为 TLS 问题已解决；服务端握手、连接负载、节点切换之间的关系仍需隔离验证。后续不应在用户主路由器上继续用该实验方案试错。

### 为什么日志看起来服务正常，电脑仍然失败

客户端日志明确记录 `SOCKS5 request granted`，然后发送 TLS ClientHello，最后得到 TLS syscall 错误。它只能说明路由器接受了请求，不能说明目标站点 TLS 已完成。

源码中 VLESS 在写入请求头后返回流，协议响应延迟到第一次读取时消费；外层 `RetryOutbound` 只处理 `connect()` 阶段的错误，接管流后的错误不会回到该重试层。SOCKS/TUN 转发错误使用 DEBUG 日志，路由器默认 INFO 没有保存相关异常。因此现有现场日志不能区分 VLESS 响应 EOF、外层 TLS 错误、Vision 解帧异常与目标连接关闭。不能把这些未记录的信息补写成确定根因，也不应贸然重放已发送的业务数据来掩盖错误。

健康检查和候选筛选在 `speedtest.rs` 中测试的是端口 80 的 HTTP 204（gstatic/Cloudflare/Google），没有验证内层 HTTPS 握手、ChatGPT 或每个固定分流节点。HTTP 检查通过不等于这些路径已经验收。

### 用户反馈的 GPT 实际走另一条固定线路

用户明确指出当时 GPT 连接不上。认证只读 `trace_route` 查询带电脑来源地址并执行 DNS 解析，返回 definitive=true：`chatgpt.com` 命中 domain-suffix 固定节点规则（配置索引 22），目标为节点 65，协议是 **VLESS Vision + TLS**，不是默认 Google 测试所走的节点，也不是上述节点 11 的 REALITY。

规则含固定节点的 ChatGPT/OpenAI 等域名，默认节点自动切换不会替换这些固定目标。本次实验取消预连接的改动也覆盖了固定 Vision 节点，但此前节点 0 的对照没有覆盖它。GPT 在故障当时没有专门的 TLS 抓取日志，不能把 Google 的 20 次失败直接当作 GPT 节点的协议错误证据。

保持回滚版本，电脑明确绑定 LAN 接口、禁用 curl 代理绕过本地代理，用路由器 DNS 给出的 Fake-IP 测试：

| 路径 | 结果 | TLS 完成 | 总耗时 |
| --- | --- | ---: | ---: |
| 电脑 → 路由器 TUN → chatgpt.com | HTTP 200 | 0.844s | 3.057s |
| 路由器 SOCKS → chatgpt.com | HTTP 200 | 1.278s | 3.211s |
| 电脑 → 路由器 TUN → auth.openai.com 根路径 | HTTP 403 | 1.948s | 2.242s |
| 路由器 SOCKS → auth.openai.com 根路径 | HTTP 403 | 1.929s | 2.177s |

403 是 HTTPS 连接完成后的站点响应，不是 TLS 连接失败。本次没有使用用户登录态，没有测试登录完成或对话流，主页成功不能替代这些验证。
