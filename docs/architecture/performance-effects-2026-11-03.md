# 路由器优化效果检查（2026-11-03）

结论：统计路径的独立开销已降低，但当前设备没有测出明显的网页访问加速；长期内存改善尚未证实。此次没有重启服务或修改配置。

## 实测

部署后的同一 daemon PID 16843 连续运行约 19 分钟。采样期间存在真实 LAN 背景流量，不是静态空载。

| 指标 | 部署前记录 | 此次检查 | 结论 |
| --- | --- | --- | --- |
| SOCKS HTTPS 总耗时 | 单次 1.341 秒 | 5 次全部 204，中位数 1.389 秒，范围 1.355–1.717 秒 | 没有加速证据 |
| 实际 TUN HTTPS 总耗时 | 单次 140 ms | 5 次全部 204，中位数 136 ms，范围 135–150 ms | 差异很小，不能归因为优化 |
| TUN 1 MiB 下载 | 没有同条件旧版基线 | 3 次完整下载，2.86–3.80 秒 | 功能正常，不能证明吞吐提升 |
| RSS | 旧进程约 38.1 MiB | 新进程早期约 25.3 MiB；此次约 27.4→29.1 MiB，后续约 32.3 MiB | 仍缓慢增长，重启/会话/负载因素没有排除 |
| 进程 CPU | 没有旧版同条件样本 | 采样各段约占单核 1–4%，包含真实背景负载 | 仅能描述现状，不能计算 CPU 节省比例 |

匿名 TUN 健康日志最新样本：223 个活跃会话、162 条活跃 TCP，packet/receive/payload 队列无积压，准入拒绝和任务错误均为 0。运行中也有 TCP peer reset 及少量 handshake reset 计数，因此不把它描述为没有任何网络异常。

流量账本继续持久化，DNS 和防火墙状态正常。API 每次仅返回前 40 行节点流量，此处聚合不能作为全进程流量总量或完整计数验收。初始 shell 中 `/proc/PID/net/tcp` 的连接数覆盖网络命名空间，也没有被当作进程连接数使用。

## 哪些优化实际作用于当前主链路

- 当前选中主节点为 **VLESS Vision**。该路径通过专门的 Vision factory 建连，绕过通用 `ConnPool`，因此普通预热池的自适应优化不直接改善这条主节点路径。规则组可能使用其他出站，不能据此说整个进程完全不会使用普通连接池。
- 当前设备约 1 GiB 总内存，普通 relay 仍使用大内存档；TUN 每方向 16 KiB 缓冲保持原策略。不能把低内存档的缓冲节省算作这台设备已获得的收益。
- 统计增量归并作用于被观察的 TCP/TUN I/O，是本次对当前主链路直接生效的主要改动。
- 大节点列表缓存属于桌面端，不影响路由器上网速度。

之前在本机构建的 release 独立微基准中，200,000 次相同归属的统计采样由逐次归并的 111–130 ms 降至批量路径 4.5–6.0 ms，验证了局部记账成本降低。这个实验不是路由器 ARM64 上的整体 CPU 或网络吞吐 A/B，不能将其倍数套用到上网体验。

进一步确认收益需要同等流量与连接规模的旧/新版对照，或者持续记录会话规模、CPU/GiB 和 RSS；本次没有为获取对照而切回旧程序打断正在使用的网络。当前数据更支持“降低统计开销、服务运行正常”，尚不支持“明显提速”或“内存已稳定”的结论。
