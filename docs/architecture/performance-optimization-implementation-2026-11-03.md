# 前四项体验优化实现与验证（2026-11-03）

承接[优化评估](performance-and-size-review-2026-11-03.md)，本次实施统计、连接池、relay 缓冲和节点列表四项。改动保留当前工作区已有协议功能；没有新增依赖。本次验证使用本机代码检查、回归与独立统计微基准，不包含路由器部署、设备 RSS/吞吐或桌面交互人工验收。

## 1. 统计热路径

`proxy/mod.rs` 中的 `ObservedIo` 保留实时全局/连接原子计数，账本改由 `traffic.rs` 的 `TrafficRecorder` 累积。稳定归属的连续采样不再逐次获取账本、session、history、subscriptions 的锁或构造月份/名称字符串。

- 持久账本的现有后台线程每秒归并增量，仍每 60 秒按脏状态持久化，不增加逐秒磁盘写入。
- 快照、月度查询、显式保存和 recorder 释放均归并剩余计数；取消和保存失败后重试保留字节。
- 作用域及账本 generation 使后续 HTTP 请求、节点/订阅归属和账本切换能重新绑定。
- 增量桶固定 UTC 日，归并时确定所属月份；跨月或时钟回退不会将旧增量记入新月份。
- 活跃 recorder 注册在账本，释放时移除，避免完成连接的条目持续积累。
- SOCKS UDP 和显式 `add_bytes_for` 等路径继续使用原有直接记账接口；此次主要优化被观察的 TCP/TUN I/O 路径。

新增验证覆盖 10,000 次采样的延迟归并、实时计数、禁用/切换账本、请求归属、订阅隔离、跨月/回拨、并发归并、取消及持久化失败重试。

release 独立微基准，每轮相同节点与订阅、200,000 次采样并校验计数一致，包含批量路径最终归并成本：

| 轮次 | 原逐次账本归并接口 | 批量 recorder |
| --- | ---: | ---: |
| 1 | 125.82 ms | 5.99 ms |
| 2 | 111.18 ms | 4.65 ms |
| 3 | 130.01 ms | 4.50 ms |

命令：`cargo test -p sockrocket-core --release --lib --offline traffic_recording_microbenchmark -- --ignored --nocapture`。这是同一构建内直接接口与批量接口的孤立比较，不是整机 CPU、网页延迟或网络吞吐提升比例；包含并发归并竞争的实际负载仍需设备测试。

## 2. 连接池

`proxy/pool.rs` 使用较小初始预热容量，按一秒需求窗口扩张；低需求窗口恢复较小目标，维护任务回收多余或过期连接。设备分档同时约束每池上限和进程所有池的预热总量，额度包含进行中的后台握手。前台按需连接不占用预热额度。

| 总内存 | 每池初始预热 | 每池上限 | 进程预热总额度 | 普通 relay 每方向缓冲 |
| --- | ---: | ---: | ---: | ---: |
| ≤300 MiB | 2 | 4 | 16 | 16 KiB |
| ≤600 MiB | 2 | 8 | 32 | 32 KiB |
| >600 MiB | 4 | 16 | 64 | 64 KiB |

闲置连接有效年龄由 120 秒调整为 30 秒，另有每五秒的回收维护。复用前进行一次非阻塞读轮询，丢弃已观察到 EOF、TLS 错误或异常提前数据的连接；这不能证明没有静默网络失效。没有加入应用数据自动重放。

后台任务不再持有公开池句柄。最后一个句柄释放时中止维护及进行中的后台握手，避免切换节点后旧池被后台工作保留。一次性测速继续使用零预热 lazy 模式。

验证覆盖突发扩容、闲置回收、全局额度、已关闭连接剔除、最后句柄释放、握手并发限制、失败重试轮数和连接超时。较少初始预热与较短闲置保留在降低负担的同时可能增加冷突发握手，需对照首字节 P95 和预热命中率。

## 3. relay 内存

普通 HTTP/SOCKS relay 按上表取缓冲，保持 Tokio 双向 half-close 与背压语义。TUN 的每方向 16 KiB 拷贝缓冲及现有 TCP 窗口/全局 payload 预算保持既有策略。设备总内存检测缓存一次，避免连接及窗口预算查询反复读取 `/proc/meminfo`。

按准入数量计算，256 MiB 档 128 条普通 relay 的双向缓冲容量由 16 MiB 降为 4 MiB；512 MiB 档 256 条由 32 MiB 降为 16 MiB。这只是拷贝缓冲容量，不代表全部进程 RSS。新增内存分档检查，替换了原先没有实际调用 relay 的测试，验证大于缓冲的完整请求、EOF 后反向响应和字节总量。

## 4. 节点列表

保留现有 `uniform_list` 可见行渲染。新增每个 AppState 独立的 `node_list::NodeListCache`，结构性编辑与测速结果分别使内容或顺序失效：

- 名称、服务器、标签的搜索文本只在内容变化时规范化。
- 协议与标签 chips 缓存复用；测速更新只重新排序，不重做搜索索引或过滤。
- 同样条件重绘直接复用排序结果；缓存不再跨窗口共享 thread-local generation。
- 手动排序使用一次旧索引到新索引映射，替代逐节点查找指纹，保留同名节点的选中、当前出站、勾选、测速标记与批次范围。
- 进行中的测速返回时先校验节点身份，排序后的结果仍落到原节点，删除/替换后的结果不写到其他节点。

纯逻辑验证覆盖 10,000 节点、元数据/排序缓存复用、中文/越南语/域名/协议检索、标签条件、重命名、删除、独立实例以及同名节点的稳定排序映射。GPUI 二进制代码检查通过；没有进行大列表实际帧耗时或桌面点击验收。
